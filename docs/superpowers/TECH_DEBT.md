# Pudu Tech Debt Ledger

Items discovered during stage reviews that were deliberately deferred. Each
stage's brainstorm should skim this for items targeted at the upcoming stage;
the planner folds them in as explicit task items. Rows marked ~~closed~~ are
kept for the record rather than deleted.

Every open row was re-checked against the code on 2026-08-30 (the branch's
final fix wave). Closing a row means striking it here in the same commit as
the code: two rows had shipped fixed-but-open, which is how the ledger stops
being trustworthy.

Re-audited 2026-09-15, after S5 shipped, against every row then targeted at a
stage that had already shipped (S2-S5). Nineteen rows were overdue. What that
audit found is the argument for doing this regularly: **four rows did not
describe the code any more.** `TD-S4-03` named an error type that does not
exist. `TD-S1-02`'s worked example (`9.10`) demonstrated nothing, because it
parses to the same f64 as `9.1` — and the row understated its own bug, which
was silent acceptance of a wrong version, not a cosmetic message. `TD-S1-08`
was filed as a one-liner and needed real plumbing. `TD-S2-01` was half dead,
overtaken by S5's reachability walk. A row that misdescribes its own defect is
worse than no row: it gets planned around.

A `target` of **`accepted`** means a deliberate limitation kept for the record,
with no work intended — not a backlog item. Rows earn it when the behaviour is
correct and the note exists only so the constraint is not rediscovered as a
bug. Retarget, do not silently pile rows onto the last stage: a stage that
accumulates every unclaimed row is a wish, not a plan.
