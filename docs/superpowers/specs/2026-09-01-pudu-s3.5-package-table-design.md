# pudu S3.5 — retire the sidecar, adopt the package table

**Status:** design
**Depends on:** S3 (`pudu vendor`, shipped in PR #5)
**Blocks:** S4 (first BUCK emitter)

---

## 1. Why this stage exists

S3 shipped a committed, deterministic file at `<third_party_dir>/pudu.lock`
recording, per package, what `pnpm-lock.yaml` omits: the tarball URL, its
sha256, its size, its archive root, its bin map, and whether it triggers an
install script. The design called it "the sidecar".

The data is not negotiable. Buck2's `http_archive` and `ctx.actions.download_file`
accept `sha1` or `sha256` and nothing else — `sha512` appears nowhere in the
buck2 prelude — while `pnpm-lock.yaml` records `sha512-…` and nothing else.
There is no derivation from one to the other; you must have the bytes. The
archive root, the bin map, and the install-script triggers likewise come only
from opening the tarball. CI on a fresh runner has no cache, so these facts
must be committed or every `buckify` becomes a full download pass.

pudu is alone among its siblings in this. `Cargo.lock` gives reindeer sha256
checksums directly; `uv.lock` gives muntjac `url`, `hash = "sha256:…"`, and
`size` directly. Neither needs a fact table. pudu does.

**What is negotiable is the framing, and the framing was wrong.** `.lock`
plus "sidecar" announces a second lockfile — a second thing a human maintains,
a second source of truth to keep in sync with `pnpm-lock.yaml`. It is neither.
It is generated output, never hand-edited, and reproducible from
`pnpm-lock.yaml` plus the network at any time.

This stage changes the name and the vocabulary. It changes no behaviour.

## 2. Scope

**In scope**

1. Rename the file: `<third_party_dir>/pudu.lock` → `<third_party_dir>/packages.toml`.
2. Reset the format version to `1`.
3. Rename the module and its types.
4. Rename `tarball.rs`'s `Manifest` to `PackageJson`.
5. Sweep diagnostics, `--help` text, and documentation for the old vocabulary.
6. Record the deferred S4 question as tech debt.

**Non-goals**

- No change to the file's format, field set, ordering, or rendering rules.
- No change to `pudu vendor`'s behaviour, its `--check` gate, the cache, the
  fetcher, or any exit code.
- No migration path for existing `pudu.lock` files. pudu is at `0.1.0` and
  unreleased; `buckify` is still unimplemented. Nobody has one.
- No decision on whether S4 promotes the table into a `load()`-ed Starlark
  file (§7).

## 3. The name

`<third_party_dir>/packages.toml`, referred to throughout as **the package
table**.

Two names were rejected for concrete reasons:

- **`vendor.toml`** collides in spirit with `vendor/`, the gitignored
  directory that vendor-mode tarballs land in — `pudu init` writes exactly
  that pattern into `<third_party_dir>/.gitignore` (`src/cli/init.rs:328`).
  A committed `vendor.toml` beside a gitignored `vendor/` invites someone to
  loosen the pattern to `vendor*` and silently stop committing the table.
- **`manifest.toml`** (muntjac's precedent for its prebake record) is vague on
  its own, and would collide with `tarball.rs`'s existing `Manifest` type,
  which means *package.json*.

`packages.toml` says what it holds, collides with nothing pudu generates
(`BUCK`, `pudu.bzl`, `config/BUCK`), and reads as generated data rather than
as a lock.

## 4. The format version

`version` resets from `2` to `1`.

The version field guards against a pudu reading a table written by a pudu with
a different schema. Because the filename changes in the same stage, no file
written by any earlier pudu can ever be read as a `packages.toml` — an old
`pudu.lock` is simply not opened. The version sequence therefore starts fresh
with the new format identity, and `version = 2` would imply a `version = 1`
`packages.toml` that never existed.

The existing `Loaded::WrongVersion` path is unchanged: a table whose version
this pudu does not write is regenerated, not rejected.

A stray `pudu.lock` left in a working tree is ignored, not deleted. pudu does
not remove files it no longer writes.

## 5. Code changes

| Before | After |
|---|---|
| `src/sidecar.rs` | `src/packages.rs` |
| `Sidecar` | `PackageTable` |
| `SIDECAR_VERSION` | `TABLE_VERSION` |
| `VendorError::SidecarMalformed` | `VendorError::TableMalformed` |
| `pudu::vendor::sidecar_malformed` | `pudu::vendor::table_malformed` |
| `tarball.rs`'s `Manifest` | `PackageJson` |

`Entry`, `Loaded`, `Expected`, `Difference`, `load`, `render`, and `staleness`
keep their names — they are unambiguous inside `packages.rs`.

The `Manifest` → `PackageJson` rename is included because it is adjacent and
becomes actively misleading otherwise: a type named `Manifest` meaning
*package.json*, sitting one module away from `PackageTable`, is a trap for
the next reader. It is `pub(crate)` with three references, so the rename is
mechanical.

`ExitCode::Stale = 5` is unchanged, as is every other exit code.

## 6. Vocabulary

"Sidecar" is retired. Diagnostics, doc comments, `--help`, and prose say
**the package table**, and error messages name `packages.toml`:

- `packages.toml has no entry for \`left-pad@1.3.0\``
- `packages.toml has an entry for \`left-pad@1.3.0\`, which is no longer needed`
- `packages.toml says version {found}; this pudu writes version {TABLE_VERSION}`
- `packages.toml is out of date ({n} difference(s))`
- help text: ``packages.toml is generated; delete it and run `pudu vendor` to rebuild it``

Documentation to update: `README.md`, the top-level design spec, the roadmap,
the S3 design spec, the S1 and S0 design specs (one mention each), and the
tarball research survey.

**The S3 implementation plan is not updated.** It is the record of what was
built and reviewed in PR #5, and rewriting it would falsify that record. The
S3 *design spec* is updated, because it describes the system as it stands.

## 7. The deferred question, recorded

A stronger design was considered and deliberately postponed: emit the table as
`vendor.bzl` holding a Starlark dict, `load()`-ed by the generated `BUCK`,
with `BUCK` carrying one explicit `npm_package` per dependency. That would
make the table a genuine build input rather than pudu's private bookkeeping,
and would keep the 300-odd rows of url/hash/size noise out of the part of
`BUCK` a human reads in review.

It was postponed because it commits S4's emitter shape before any emitter
exists, and because it requires a restricted Starlark reader in pudu — a new
module with a new escaping surface that must stay in lockstep with the writer.
Neither cost is justified while the file has no build consumer.

This is recorded in the roadmap as **TD-S4-01** so S4 decides it deliberately,
with a real emitter in hand, rather than rediscovering it.

## 8. Testing

No new behaviour, so no new behavioural tests. The existing suite is updated
in place: `tests/vendor.rs`, `tests/vendor_oracle.rs`, the unit tests in
`packages.rs`, and the `--help` snapshot.

One test is added: `an_old_pudu_lock_is_not_read_as_a_package_table` — a
working tree containing a valid `pudu.lock` and no `packages.toml` is treated
as having no table at all, and `--check` reports every package missing rather
than reading the old file. This pins §4's claim that the rename makes the
version reset safe.

## 9. Exit criteria

The stage passes when S3's exit criteria still hold verbatim, with
`packages.toml` substituted for `pudu.lock`. Each is re-verified by hand on
the 400-package fixture, not merely by the test suite:

1. `pudu vendor` writes a deterministic, sorted `packages.toml` covering the
   pruned union; a second run reproduces it byte-identically.
2. A tarball failing the lockfile's sha512 aborts with an error naming the
   package, the URL, and both hashes, and writes no table.
3. `pudu vendor --check` exits 5 when stale, 0 when current, and opens no
   socket in either case.
4. `--no-network` succeeds against a warm cache and errors against a cold one,
   naming the missing package and its URL.
5. A scoped-registry override resolves to the right host and the resolved URL
   is recorded in the table.
6. `has_install_script` is true for `esbuild@0.25.12`.
7. `@babel/parser`'s bin is recorded as `parser`, not `@babel/parser`.
8. The word "sidecar" appears nowhere in `src/`, `tests/`, `README.md`, or
   any spec other than this one. `pudu.lock` survives only where it names
   history or the thing being retired: `docs/superpowers/plans/`, this spec,
   and the `an_old_pudu_lock_is_not_read_as_a_package_table` test.

Plus the standing gates: `cargo fmt --all -- --check`, `cargo clippy
--all-targets -- -D warnings`, `cargo +1.88 check --all-targets`, and the
network-gated oracle against `registry.npmjs.org`.

## 10. Tech debt

  oracle special-case), **TD-S2-06** (constraint-label collision, targeted at
