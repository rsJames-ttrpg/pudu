# npm tarball, bin, and install-script survey

**Date:** 2026-08-31
**For:** pudu S3 (`pudu vendor` and the `pudu.lock` sidecar)
**Method:** run the real thing. 400 live registry manifests (every `packages:`
entry of `tests/fixtures/lock/real/pnpm-lock.yaml`), pnpm's own published
resolution code, and probe lockfiles generated by pnpm 10.21.0.

Everything below is an observation, not a reading of documentation. Where a
claim rests on pnpm's source, the package and the exact expression are quoted.

---

## 1. Registry URL derivation: 400 / 400 exact

The rule under test:

```
<registry>/<name>/-/<basename>-<version>.tgz      basename = name after the last '/'
```

Compared against `dist.tarball` as served by registry.npmjs.org for all 400
fixture packages: **zero mismatches**. The set includes 130 scoped names
(`@babel/*`, `@esbuild/*`, `@sveltejs/*`), so the scope-stripping half of the
rule is exercised heavily rather than incidentally.

Spot checks outside the fixture confirm the rule survives version shapes the
fixture lacks — prerelease (`@babel/core@7.0.0-beta.4`), dated dev builds
(`typescript@7.1.0-dev.20260831.1`), and the earliest published version of
several packages (`esbuild@0.0.0`, `graceful-fs@1.0.0`).

Design §12 calls this derivation "a heuristic". On the public registry it is
not: it is exact across every case reachable from a real lockfile. The
heuristic label belongs to *private* registries, which is why `pudu.lock`
records the resolved URL.

**Integrity algorithms:** all 400 are `sha512`. No `sha1-` prefixed integrity
appears, including for packages published in 2013 (`graceful-fs@1.2.3`) —
npm now serves sha512 in the packument regardless of publication date. A
`sha1` code path is therefore unreachable from the public registry, though
nothing rules it out for a private one.

## 2. pnpm's install-script rule reads the tarball, not just `package.json`

From `@pnpm/building.pkg-requires-build`, verbatim:

```js
export function pkgRequiresBuild (manifest, filesIndex) {
  return Boolean(manifest?.scripts != null && (Boolean(manifest.scripts.preinstall) ||
    Boolean(manifest.scripts.install) ||
    Boolean(manifest.scripts.postinstall)) ||
    filesIncludeInstallScripts(filesIndex))
}
function filesIncludeInstallScripts (filesIndex) {
  const keys = filesIndex instanceof Map ? filesIndex.keys() : Object.keys(filesIndex)
  for (const filename of keys) {
    if (filename === 'binding.gyp') return true
    if (filename.match(/^\.hooks[\\/]/) != null) return true
  }
  return false
}
```

Three triggers, not one:

1. `scripts.preinstall`, `scripts.install`, or `scripts.postinstall`
2. a `binding.gyp` at the package root
3. any entry under `.hooks/`

Design §4 describes this as "`package.json` inspection". That is **incomplete**
— triggers 2 and 3 are properties of the tarball's file list. A package with a
`binding.gyp` and no scripts at all still requires a build, and pudu would have
reported `has_install_script = false` for it.

**Trigger 1 has live instances in the fixture; triggers 2 and 3 have none.**
`esbuild@0.25.12` and `esbuild@0.28.2` both carry `"postinstall": "node
install.js"` in their published tarballs. Two of 400.

An earlier revision of this section claimed a third — `fsevents@2.3.3`, said to
carry `"install": "node-gyp rebuild"` and `gypfile: true`, and so to be a live
instance of trigger 2 as well as trigger 1. **That is wrong, and it was checked
by hand.** Its sha512-verified tarball contains no `binding.gyp`, no `gypfile`
field, and no `install`, `preinstall`, or `postinstall` script; its scripts are
`clean`, `build`, `test`, and `prepublishOnly`, and it ships a prebuilt
`fsevents.node` instead. Only the registry's packument says otherwise, and that
metadata is stale for this one field on this one version. Real pnpm's
`pkgRequiresBuild` reads the manifest and the file index back from the
*extracted tarball*, never the registry API, so pnpm would compute `false` here
too. See TECH_DEBT TD-S3-03 for the full trail, and `tests/vendor_oracle.rs`,
which already encodes the truth by asserting `has_install_script == false`.

So triggers 2 (`binding.gyp`) and 3 (`.hooks/`) have **no live instance
anywhere in this fixture**. They are real pnpm rules and pudu implements them,
but they are covered only by synthetic tarballs built in `src/tarball.rs`'s
unit tests. A future implementer must not go looking for `fsevents` as the
worked example of `binding.gyp`; it is not one.

`fsevents` is `os: [darwin]`, so on a linux-only platform config it is pruned
before the vendor pass ever sees it — the S6 script gate and S2's pruning
interact, and a test asserting the gate fires must configure a darwin platform.
`esbuild` is platform-independent, so it is the package to reach for when a
test needs an install script that survives any platform config.

## 3. Bin resolution also needs the file list

From `@pnpm/package-bins@1000.0.16`, the rules in force:

- `manifest.bin` as a **string** maps to one command named after the package,
  with a leading scope stripped: `commandName[0] === '@' ? slice(indexOf('/') + 1)`.
- `manifest.bin` as an **object** takes its keys as command names, with the
  same scope strip applied per key.
- A command name is **dropped** when `binName !== encodeURIComponent(binName)`,
  unless it is exactly `$`.
- A command is **dropped** when its resolved path escapes the package
  directory (`is-subdir`).
- With no `bin` at all, `directories.bin` is globbed **recursively**
  (`glob('**', {onlyFiles: true})`) and each file becomes a command named
  `path.basename(file)` — so nested files collapse to bare basenames.

The `directories.bin` branch cannot be served from `package.json` alone.
Combined with §2, the vendor pass must enumerate tar entry names. Since the
tarball is already being streamed to hash it, this costs nothing extra.

**Distribution across the 400:** 1 string form, 26 object form, 373 with no
`bin`, and **zero** using `directories.bin`. The single string-form package is
`@babel/parser` — scoped, so it exercises the scope-strip rule: its command is
`parser`, not `@babel/parser`. No object-form package uses a scoped key, and
none uses a name needing the `encodeURIComponent` rejection. Those branches
need synthetic tarballs; the fixture will not reach them.

**`hasBin` provenance:** the lockfile marks exactly 27 packages `hasBin: true`,
and exactly 27 manifests carry a `bin` field — the same 27. On this corpus
`hasBin` ⟺ `bin` present, with `directories.bin` unrepresented. That makes
`hasBin` a usable cross-check but not a source of truth: pudu computes the map
from the tarball and treats disagreement as a warning.

## 4. Non-registry resolutions, and one that S1 anticipated

A probe lockfile installing a `github:` specifier produces:

```yaml
  is-plain-obj@https://codeload.github.com/sindresorhus/is-plain-obj/tar.gz/3b33a59bd31fdee17acebeb0f9e39b6eca007719:
    resolution: {tarball: https://codeload.github.com/sindresorhus/is-plain-obj/tar.gz/3b33a59bd31fdee17acebeb0f9e39b6eca007719}
    version: 4.1.0
    engines: {node: '>=12'}
```

Three properties matter. There is **no integrity field at all** — nothing to
verify the bytes against. The key's version segment is a URL, and a separate
`version:` field carries the real semver. And a codeload tarball is not
npm-shaped: it nests under `<repo>-<sha>/`, not `package/`, and typically needs
a `prepare` script run to be usable.

Two shapes that look similar are not:

- `resolution: {tarball: …, integrity: sha512-…}` — the **private-registry**
  shape. `src/lock/types.rs` already orders `Tarball` before `Integrity` in the
  untagged enum precisely so this does not silently degrade to a public-registry
  fetch. It has a hash, so it is verifiable, and S3 supports it by fetching the
  recorded URL verbatim.
- `resolution: {tarball: …}` with no integrity — unverifiable. Rejected.

A separate probe confirms pnpm **normalises** an `https://` specifier that
happens to point at a registry tarball: `"https://registry.npmjs.org/is-odd/-/is-odd-3.0.1.tgz"`
resolves to an ordinary `is-odd@3.0.1` entry with integrity. Only genuinely
off-registry URLs produce the unverifiable shape.

## 5. What the registry manifests give S3 for free

Fetching `https://registry.npmjs.org/<name>/<version>` returns the full
manifest, including `bin`, `directories`, `scripts`, and `gypfile` — the
abbreviated packument (`Accept: application/vnd.npm.install-v1+json`) omits all
of them, which is the same asymmetry the [S2 platform survey](2026-08-31-pnpm-platform-matching-survey.md)
found for `libc`.

That makes a 400-row capture an independent oracle for three of the four
fields `pudu vendor` records — `url`, `bin`, `has_install_script` — obtained
without downloading a single tarball. It cannot supply `sha256` or `size`,
which exist only in the bytes.

The manifest is a *cross-check*, not the truth: it is derived from the
tarball's `package.json` at publish time, and `directories.bin` and
`binding.gyp` cases resolve differently from it than from the archive. Where
they disagree, the tarball wins and the disagreement is the finding.

## 6. Assumptions this survey overturned

| Assumption | Reality |
|---|---|
| Install scripts are a `package.json` property | Also `binding.gyp` and `.hooks/` — file-list properties (§2) |
| The `bin` map is a `package.json` property | `directories.bin` needs the file list too (§3) |
| A string `bin` is named after the package | Named after the package *with the scope stripped* (§3) |
| URL derivation is a heuristic everywhere | Exact on the public registry, 400/400; heuristic only off it (§1) |
| `resolution.tarball` means "unverifiable, reject" | Two distinct shapes; the private-registry one carries integrity (§4) |
| Old packages may carry `sha1` integrity | Not from the public registry — all 400 are sha512 (§1) |
